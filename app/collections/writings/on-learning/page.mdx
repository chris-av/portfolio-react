# On Learning New Technologies

The half-life of any specific technical skill is shorter than it used to be. Frameworks come and go. The engineers who stay relevant aren't the ones who memorize APIs — they're the ones who know how to learn.

## The Build-First Approach

Reading documentation is useful. Building something with the technology is better. You learn different things from each, and the things you learn from building stick longer.

My default when picking up something new:

- Read just enough to get started
- Build the smallest thing that could work
- Hit a wall, read more, build again

### What This Looks Like in Practice

When I first started working with React, I didn't read the full docs front to back. I built a small component, ran into state management confusion, read exactly the part of the docs that addressed it, and kept going.

That cycle — build, get stuck, read, repeat — is faster than top-down learning for most things.

## The Role of Discomfort

There's a specific kind of frustration that comes right before a concept clicks. It feels like spinning your wheels, but you're actually about to make progress. Learning to recognize that feeling and not run from it is most of the battle.

> Being a beginner is uncomfortable. Being comfortable with being a beginner is a superpower.

## What Transfers

The good news is that a lot transfers. If you understand how one database's query planner works, you have a framework for understanding others. If you've debugged one production incident thoroughly, you know how to approach the next one.

The specifics change. The thinking doesn't.
